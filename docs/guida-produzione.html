1Directus CMS — Hosting e configurazione

1.1 Requisiti hosting

Directus richiede un host con supporto Node.js 18+ oppure Docker. Le opzioni più comuni per progetti client:

  • cPanel con Node.js Selector — soluzione economica, supportata dalla maggior parte dei provider condivisi (es. SiteGround, Aruba, Namecheap)
  • VPS con Docker — maggior controllo, consigliato per progetti ad alto traffico
  • Railway / Render — deploy in un click con immagine Docker ufficiale directus/directus

1.2 Database MySQL

  • Crea un database MySQL 8+ dedicato al progettoDa cPanel → Database Wizard, oppure da phpMyAdmin
  • Crea un utente MySQL con tutti i permessi sul databaseSegna: host, nome DB, utente, password — ti serviranno nella configurazione Directus

1.3 Installazione Directus

# Via npm (su VPS o cPanel con Node.js)
npm init directus-project@latest ./cms
# Seleziona: MySQL → inserisci credenziali DB
# Crea admin email + password

# Oppure via Docker
docker run -p 8055:8055 \
  -e DB_CLIENT=mysql \
  -e DB_HOST=db-host \
  -e DB_PORT=3306 \
  -e DB_DATABASE=nome_db \
  -e DB_USER=utente_db \
  -e DB_PASSWORD=password_db \
  -e SECRET=stringa_casuale_32_chars \
  directus/directus

1.4 Generare il token statico (DIRECTUS_TOKEN)

Il token statico è la chiave che il frontend usa per autenticarsi alle API Directus.

  • Accedi al pannello admin Directus https://cms.tuodominio.it/admin
  • Vai su Settings → Users → Admin (o crea un utente dedicato "API Bot" con ruolo Admin)
  • Scorri fino a Token → clicca Regenerate Token
  • Copia il token generato (visibile una sola volta) → incollalo in DIRECTUS_TOKEN
Attenzione: Usa un utente dedicato "API Bot" separato dall'admin personale. Se cambi la password dell'admin, il token rimane valido; se si disabilita l'utente, il token smette di funzionare.

1.5 Creare le collezioni con lo script

# Nella root del progetto, con .env configurato
node scripts/setup-collections.mjs

Crea automaticamente tutte le collezioni: pages, posts, categories, portfolio, faq, site_settings, products, product_categories, product_variants, shipping_zones, orders, order_items, customers, coupons, gift_cards, contact_submissions.

1.6 Configurare i permessi

  • Settings → Roles → Public: permesso read su pages, posts, categories, portfolio, faq, site_settings, products, product_categories
  • Crea ruolo Customer: read su orders (filtro: customer_email = $CURRENT_USER.email)
  • Il ruolo Admin ha accesso completo (non modificare)

2Stripe — Pagamenti e webhook

2.1 Creare account e ottenere le chiavi API

  • Crea account su dashboard.stripe.com (o accedi se già esistente)
  • Completa la verifica identità per attivare i pagamenti reali
  • Vai su Developers → API keys
  • Copia Publishable key (pk_live_...) → STRIPE_PUBLISHABLE_KEY
  • Clicca Reveal live key, copia Secret key (sk_live_...) → STRIPE_SECRET_KEYLa secret key è visibile una sola volta. Salvala subito in un password manager.
Differenza test/live: In sviluppo usa le chiavi pk_test_... / sk_test_.... Le carte di test sono disponibili su docs.stripe.com/testing. Carta di test universale: 4242 4242 4242 4242, qualsiasi scadenza futura, qualsiasi CVC.

2.2 Configurare il webhook

Il webhook notifica il backend quando un pagamento è completato.

  • Vai su Developers → Webhooks → Add endpoint
  • Endpoint URL: https://tuodominio.it/api/webhook/stripe
  • Events: seleziona checkout.session.completed
  • Clicca Add endpoint → vai su Signing secret → copia il valore whsec_... → STRIPE_WEBHOOK_SECRET
In sviluppo locale: usa Stripe CLI per forwardare gli eventi. Installa da stripe.com/docs/stripe-cli poi esegui:
stripe listen --forward-to localhost:4321/api/webhook/stripeIl CLI stampa un webhook secret temporaneo (whsec_...) da usare in .env durante lo sviluppo.

3Google reCAPTCHA v3

  • Vai su google.com/recaptcha/admin → accedi con account Google
  • Clicca + per registrare un nuovo sito
  • Label: nome del progetto. Tipo: Score based (v3)
  • Domains: inserisci tuodominio.it (senza https://). Aggiungi anche localhost per sviluppo
  • Copia Site Key → PUBLIC_RECAPTCHA_SITE_KEYQuesta chiave è pubblica e va nel bundle JS del frontend
  • Copia Secret Key → RECAPTCHA_SECRET_KEYQuesta chiave è privata, usata solo server-side per verificare il token
Score: reCAPTCHA v3 assegna uno score da 0.0 (bot) a 1.0 (umano). Il valore minimo accettato è configurabile con RECAPTCHA_MIN_SCORE (default: 0.5). Abbassa a 0.3 se ricevi falsi positivi da utenti legittimi.

4Netlify — Deploy e configurazione

4.1 Creare il sito

  • Netlify → Add new site → Import an existing project
  • Connetti GitHub → seleziona la repo del cliente
  • Build command: npm run build
  • Publish directory: dist
  • Node version: 22 (Site settings → Environment → Node version, oppure aggiungi NODE_VERSION=22 nelle env vars)

4.2 Variabili d'ambiente su Netlify

Vai su Site settings → Environment variables e aggiungi tutte le variabili del .env:

Attenzione ai prefissi: Le variabili con prefisso PUBLIC_ sono esposte nel browser (bundle JS). Tutte le altre sono accessibili solo server-side. Non mettere mai segreti in variabili PUBLIC_.

4.3 Build hook per Directus

  • Netlify → Site settings → Build hooks → Add build hook
  • Nome: "Directus Publish" → copia l'URL del hook
  • In Directus → Settings → Flows → crea un flow con trigger "Action" su save/publish di pages, posts, products
  • Aggiungi step "Webhook" → incolla l'URL Netlify (metodo POST)

4.4 ALLOWED_ORIGIN per le API

La variabile ALLOWED_ORIGIN protegge le API da richieste cross-origin non autorizzate. Deve corrispondere esattamente all'URL del sito (senza slash finale):

ALLOWED_ORIGIN=https://tuodominio.it   # NO slash finale
Non usare * in produzione: esporrebbe il checkout e le API a chiamate da qualsiasi origine.

5Backup automatico

5.1 Generare BACKUP_ADMIN_KEY

La chiave protegge l'endpoint /api/admin/backup da accessi non autorizzati. Deve essere una stringa casuale sicura:

# Genera una chiave sicura con Node.js
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

# Oppure con openssl
openssl rand -hex 32

Copia l'output → BACKUP_ADMIN_KEY. Usa la stessa chiave su Netlify e nel file .env locale.

5.2 Schedule automatico

La Netlify Scheduled Function si attiva in base al valore di BACKUP_CRON:

BACKUP_CRON=@daily        # ogni giorno a mezzanotte UTC (default)
BACKUP_CRON=0 2 * * *    # ogni giorno alle 02:00 UTC
BACKUP_CRON=@weekly       # ogni domenica

5.3 Storage S3 (opzionale)

Per archiviare i backup su cloud (AWS S3, Backblaze B2, Cloudflare R2, MinIO):

  • Crea un bucket S3 dedicato al progetto
  • Crea un utente IAM con permesso s3:PutObject sul solo bucket
  • Genera Access Key + Secret Key per l'utente IAM
  • Imposta BACKUP_STORAGE=s3 e compila tutte le variabili BACKUP_S3_*

6Go-Live — DNS e checklist finale

6.1 Dominio su Netlify

  • Netlify → Domain management → Add custom domain
  • Sul provider DNS crea record: CNAME www → nome-sito.netlify.app
  • Per il dominio apex (@): usa i Netlify DNS (nameserver) oppure un record A → 75.2.60.5
  • Abilita HTTPS (automatico con Let's Encrypt dopo propagazione DNS)
  • Attendi propagazione DNS: da 15 minuti a 48 ore (media: 1-2 ore)

6.2 Smoke test

  • Homepage, blog, portfolio si caricano correttamente
  • Negozio: lista prodotti, categoria, scheda prodotto
  • Aggiungi prodotto al carrello → badge aggiornato
  • Checkout con carta test Stripe (4242 4242 4242 4242)
  • Pagina success: ordine creato, link download per prodotti digitali
  • Webhook Stripe: verifica in Stripe Dashboard → Webhooks → last events
  • Form contatti: invio → verifica su Directus + eventuale email
  • Area account: login, lista ordini, dettaglio ordine
  • Backup manuale: npm run backup -- --dry-run → verifica output
  • Build hook: pubblica un contenuto su Directus → verifica deploy automatico su Netlify

Backup automatico
Variabile Descrizione e dove trovarla
BACKUP_ADMIN_KEY RICHIESTA Chiave segreta per proteggere l'endpoint /api/admin/backup.
Genera con: node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
→ Genera localmente, copia su Netlify nelle env vars
BACKUP_STORAGE OPZIONALE Tipo di storage per i backup. Valori: local (default) oppure s3.
→ Imposta manualmente. Usa s3 per backup remoti su AWS/Backblaze/R2
BACKUP_LOCAL_PATH OPZIONALE Percorso locale dove salvare i backup. Default: ./backups.
→ Imposta solo se vuoi un percorso personalizzato
BACKUP_CRON OPZIONALE Schedule per il backup automatico (Netlify Scheduled Function). Default: @daily.
Esempi: @daily, @weekly, 0 2 * * * (ogni notte alle 2 UTC).
→ Imposta su Netlify nelle env vars
BACKUP_S3_ENDPOINT OPZIONALE Endpoint S3-compatible. Solo se BACKUP_STORAGE=s3.
Es: https://s3.eu-central-1.amazonaws.com, https://s3.eu-central-003.backblazeb2.com
→ Dal pannello del provider S3 (AWS, Backblaze B2, Cloudflare R2, MinIO)
BACKUP_S3_BUCKET OPZIONALE Nome del bucket S3.
→ AWS S3 → Buckets → nome del bucket creato
BACKUP_S3_REGION OPZIONALE Regione AWS del bucket. Default: eu-central-1.
Es: us-east-1, eu-west-1
→ Visible nella console AWS durante creazione bucket
BACKUP_S3_ACCESS_KEY OPZIONALE Access Key ID dell'utente IAM dedicato ai backup.
→ AWS Console → IAM → Users → [utente backup] → Security credentials → Create access key
BACKUP_S3_SECRET_KEY OPZIONALE Secret Access Key IAM. Visibile solo al momento della creazione.
→ AWS IAM → create access key → copia e salva subito (non è recuperabile)
BACKUP_S3_PREFIX OPZIONALE Prefisso (cartella virtuale) dentro il bucket. Default: backups/.
Utile per organizzare più progetti nello stesso bucket: cliente-x/backups/
→ Imposta manualmente
