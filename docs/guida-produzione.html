1Directus CMS — Hosting e configurazione

1.1 Requisiti hosting

Directus richiede un host con supporto Node.js 18+ oppure Docker. Le opzioni più comuni per progetti client:

  • cPanel con Node.js Selector — soluzione economica, supportata dalla maggior parte dei provider condivisi (es. SiteGround, Aruba, Namecheap)
  • VPS con Docker — maggior controllo, consigliato per progetti ad alto traffico
  • Railway / Render — deploy in un click con immagine Docker ufficiale directus/directus

1.2 Database MySQL

  • Crea un database MySQL 8+ dedicato al progettoDa cPanel → Database Wizard, oppure da phpMyAdmin
  • Crea un utente MySQL con tutti i permessi sul databaseSegna: host, nome DB, utente, password — ti serviranno nella configurazione Directus

1.3 Installazione Directus

Scegli l'opzione corrispondente al tuo hosting.

▸ Opzione A — cPanel con Node.js Selector

Adatta a provider condivisi (SiteGround, Aruba, Namecheap). Richiede accesso SSH e cPanel con Node.js Selector abilitato.

  • In cPanel → Domains → Subdomains: crea il sottodominio cms.tuodominio.itDirectus va sempre su un sottodominio dedicato (es. cms., admin., api.) — non nella root del dominio principale dove vive il frontend.
  • Accedi via SSH e crea la cartella del progetto fuori da public_html 
    ssh utente@tuoserver.it
mkdir ~/cms
    La cartella è fuori da public_html — i file Node.js (incluso .env) non devono essere web-accessibili.
  • In cPanel → Setup Node.js App: crea l'applicazione prima di installare i pacchetti — questo genera il virtual environment che rende npm disponibile via SSH
    CampoValore
    Node.js version20.x o 22.x
    Application modeProduction
    Application rootcms (path relativo alla home, fuori da public_html)
    Application URLhttps://cms.tuodominio.it
    Application startup fileserver.js
  • Dal pannello dell'app appena creata, copia il comando Enter to virtual environment (es. source /home/utente/nodevenv/cms/22/bin/activate) ed eseguilo in SSH — da questo momento npm e node sono disponibili nella sessione 
    source /home/utente/nodevenv/cms/22/bin/activate
cd ~/cms
  • Installa Directus 
    npm init -y
npm install directus
  • Genera il valore per SECRET direttamente via SSH 
    node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
    Copia l'output (stringa esadecimale da 64 caratteri) — ti serve nel passaggio successivo.
  • Crea il file ~/cms/.env 
    DB_CLIENT=mysql
DB_HOST=localhost
DB_PORT=3306
DB_DATABASE=nome_db
DB_USER=utente_db
DB_PASSWORD=password_db
SECRET=stringa_hex_generata_sopra
ADMIN_EMAIL=admin@tuodominio.it
ADMIN_PASSWORD=password_sicura
PUBLIC_URL=https://cms.tuodominio.it
  • Esegui il bootstrap (crea le tabelle di sistema Directus) 
    npx directus bootstrap
  • Crea il file ~/cms/server.js — wrapper richiesto da cPanel (non supporta npm start direttamente) 
    // server.js
const { spawn } = require('child_process')
const proc = spawn(
  'node_modules/.bin/directus',
  ['start'],
  { stdio: 'inherit', env: process.env }
)
proc.on('close', code => process.exit(code))
  • Torna in cPanel → Node.js App → clicca Restart
Porta: cPanel inietta automaticamente la variabile PORT nell'ambiente. Directus la legge nativamente — non serve configurarla nel .env.
▸ Opzione B — Railway con Docker

Deploy completamente gestito. Railway esegue l'immagine ufficiale directus/directus e fornisce un database PostgreSQL come servizio collegato.

  • Crea un progetto su railway.app → New Project → Deploy from Docker Image
  • Immagine: directus/directus:latest
  • Aggiungi un servizio PostgreSQL al progetto (tasto + → Database → PostgreSQL)
  • Nel servizio Directus → Variables → aggiungi: 
    DB_CLIENT=pg
DATABASE_URL=${{Postgres.DATABASE_URL}}
SECRET=stringa_casuale_32_chars
ADMIN_EMAIL=admin@tuodominio.it
ADMIN_PASSWORD=password_sicura
PUBLIC_URL=https://cms.tuodominio.up.railway.app
    La sintassi ${{Postgres.DATABASE_URL}} è il riferimento Railway al servizio PostgreSQL; viene risolta automaticamente.
  • Nel servizio Directus → Settings → Volumes: aggiungi un volume montato su /directus/uploads per rendere i file persistenti tra i redeploy
  • Vai su Settings → Networking → Generate Domain per ottenere l'URL pubblico del CMS
Bootstrap automatico: directus/directus esegue directus bootstrap all'avvio se il database è vuoto — non serve eseguirlo manualmente su Railway.
▸ Opzione C — Render con Docker

Simile a Railway. Render offre un piano gratuito con limitazioni (il servizio va in sleep dopo 15 min di inattività — non adatto a produzione). Usa il piano Starter ($7/mese) per un servizio always-on.

  • Crea un Web Service su render.com → scegli Deploy an existing image
  • Image URL: docker.io/directus/directus:latest
  • Crea un database PostgreSQL separato su Render → copia le credenziali
  • Nel Web Service → Environment → aggiungi: 
    DB_CLIENT=pg
DB_HOST=hostname-db.render.com
DB_PORT=5432
DB_DATABASE=nome_db
DB_USER=utente_db
DB_PASSWORD=password_db
SECRET=stringa_casuale_32_chars
ADMIN_EMAIL=admin@tuodominio.it
ADMIN_PASSWORD=password_sicura
PUBLIC_URL=https://cms-tuoprogetto.onrender.com
  • Nel Web Service → Disks: aggiungi un persistent disk montato su /directus/uploads (es. 1 GB)
Piano gratuito: Render mette in sleep i servizi gratuiti dopo 15 minuti di inattività. La prima richiesta dopo lo sleep impiega ~30 secondi. Usa il piano Starter per produzione.
▸ Opzione D — VPS nativo (Ubuntu + PM2) consigliato

Adatta a chi ha già un VPS Ubuntu con Nginx e PM2. Directus gira come processo Node nativo — nessun Docker, nessun cPanel.

  • Crea la directory del progetto come root e assegnala all'utente applicativo 
    mkdir -p /var/www/cliente/cms
chown -R deploy:deploy /var/www/cliente
  • Aggiungi subito il record DNS per il sottodominio CMS nel pannello del tuo provider
    TipoNomeValoreTTL
    AcmsIP VPS300
    Fallo subito — il DNS impiega qualche minuto a propagarsi, e puoi proseguire con i passi seguenti nel frattempo.
  • Crea il vhost Nginx per il CMS (come root) 
    nano /etc/nginx/sites-available/cms.tuodominio.it
    Incolla il seguente contenuto: 
    server {
    server_name cms.tuodominio.it;

    # Obbligatorio prima del proxy — altrimenti certbot
    # riceve la risposta di Directus invece del file di verifica.
    location /.well-known/acme-challenge/ {
        root /var/www/html;
    }

    location / {
        proxy_pass http://127.0.0.1:8055;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }

    listen 80;
}
    Abilita il sito e ricarica Nginx: 
    ln -s /etc/nginx/sites-available/cms.tuodominio.it /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx
  • Verifica la propagazione DNS e ottieni il certificato SSL per il CMS 
    dig +short cms.tuodominio.it    # deve restituire l'IP del VPS
    Quando il dig restituisce l'IP corretto, installa certbot se necessario e rilascia il certificato: 
    certbot --version 2>/dev/null || apt install -y certbot python3-certbot-nginx
certbot --nginx -d cms.tuodominio.it
    Certbot aggiorna automaticamente il vhost con le direttive SSL e il redirect HTTP→HTTPS.
Per creare il vhost di staging (staging.tuodominio.it) e quello di produzione (tuodominio.it) fai riferimento alla sezione 4.7 — Nginx vhost (frontend).
  • Passa all'utente applicativo e verifica che nvm sia disponibile 
    su - deploy
nvm --version
    Se nvm non è installato: curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.0/install.sh | bash poi riapri la sessione.
  • Installa Node 22 e impostalo come versione attiva 
    nvm install 22
nvm use 22
node --version   # deve mostrare v22.x
    Node 22 è richiesto sia da Directus che dal build di Astro. Alcune dipendenze native (es. isolated-vm) hanno prebuilt per arm64 solo da Node 22 in su — su Node 20 l'installazione fallisce se mancano i build tools.
  • Installa Directus 
    cd /var/www/cliente/cms
npm init -y
npm install directus
  • Genera il SECRET 
    node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
    Copia l'output — ti serve nel passaggio successivo.
  • Crea il database MySQL e l'utente dedicato (da root o utente con privilegi) 
    mysql -u root -p
    All'interno del prompt MySQL esegui: 
    -- sostituisci i valori evidenziati
CREATE DATABASE nome_db
  CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

CREATE USER 'utente_db'@'localhost'
  IDENTIFIED BY 'password_sicura';

GRANT ALL PRIVILEGES ON nome_db.*
  TO 'utente_db'@'localhost';

FLUSH PRIVILEGES;
EXIT;
    Usa credenziali dedicate per ogni progetto — mai usare root nel .env di Directus.
  • Crea il file .env 
    DB_CLIENT=mysql
DB_HOST=localhost
DB_PORT=3306
DB_DATABASE=nome_db
DB_USER=utente_db
DB_PASSWORD=password_db
SECRET=stringa_hex_generata_sopra
ADMIN_EMAIL=admin@tuodominio.it
ADMIN_PASSWORD=password_sicura
PUBLIC_URL=https://cms.tuodominio.it
PORT=8055
    Se sul server gira già un altro Directus sulla porta 8055, usa una porta diversa (es. PORT=8056). Ricorda di aggiornare anche il vhost Nginx. Non confondere PORT (porta HTTP di Directus) con DB_PORT (porta MySQL — sempre 3306).
  • Bootstrap del database 
    npx directus bootstrap
  • Crea le directory necessarie e assegna i permessi corretti (come root) 
    mkdir -p /var/www/cliente/cms/uploads
mkdir -p /var/www/cliente/cms/extensions
chown -R deploy:deploy /var/www/cliente/cms/uploads /var/www/cliente/cms/extensions
    Directus non parte se queste directory non sono leggibili/scrivibili dall'utente applicativo.
  • Installa PM2 globalmente per la versione Node attiva 
    npm install -g pm2
    PM2 va installato per ogni versione Node gestita da nvm — se cambi versione Node dovrai reinstallarlo.
  • Avvia Directus con PM2 
    pm2 start node_modules/.bin/directus --name "cms-cliente" -- start
pm2 save
  • Verifica che Directus sia partito correttamente 
    pm2 logs cms-cliente --lines 20
    Deve comparire Server started. Se vedi ancora errori di porta, controlla che il PORT nel .env sia libero con: 
    ss -tlnp | grep 8055
Porta già in uso (più istanze Directus sullo stesso server): se i log mostrano Port 8055 is already in use, modifica PORT=8056 (o altra porta libera) nel .env, aggiorna il proxy_pass nel vhost Nginx e riavvia con pm2 restart cms-cliente. Non modificare DB_PORT — quella è la porta di MySQL e deve rimanere 3306.
MySQL già installato: Se MySQL è già presente sul server, salta l'installazione e usa direttamente il prompt mysql -u root -p per creare database e utente come indicato sopra.

1.4 Generare il token statico (DIRECTUS_TOKEN)

Il token statico è la chiave che il frontend usa per autenticarsi alle API Directus.

  • Accedi al pannello admin Directus https://cms.tuodominio.it/admin
  • Vai su Settings → Users → Admin (o crea un utente dedicato "API Bot" con ruolo Admin)
  • Scorri fino a Token → clicca Regenerate Token
  • Copia il token generato (visibile una sola volta) — salvalo in un posto sicuro. Va incollato nel file .env del progetto Astro (in locale) al passo 1.5: 
    DIRECTUS_TOKEN=token_copiato_qui
Attenzione: Usa un utente dedicato "API Bot" separato dall'admin personale. Se cambi la password dell'admin, il token rimane valido; se si disabilita l'utente, il token smette di funzionare.

1.5 Creare il progetto in locale

La repo va creata in locale prima di eseguire gli script di configurazione e il deploy del frontend.

  • Crea la repo del cliente dal template GitHub e clonala in locale 
    gh repo create nome-cliente --template simone-bernazzi/astro-directus-ecommerce --private --clone
cd nome-cliente
    Richiede GitHub CLI (gh). In alternativa: crea la repo dal sito GitHub → "Use this template" → clona con git clone.
  • Attiva Node 22 e installa le dipendenze 
    nvm use 22
npm install
  • Crea il file .env locale dal template e compila le variabili Directus 
    cp .env.example .env
    Apri .env e imposta almeno: 
    DIRECTUS_URL=https://cms.tuodominio.it
DIRECTUS_TOKEN=token_generato_al_passo_1.4
PUBLIC_SITE_URL=https://staging.tuodominio.it
    PUBLIC_SITE_URL deve corrispondere al dominio su cui il frontend è raggiungibile. In fase di staging usa https://staging.tuodominio.it; quando vai in produzione cambialo in https://tuodominio.it e rideploya (vedi sezione 7).

1.6 Creare le collezioni con lo script (da locale)

Lo script va eseguito in locale dalla root della repo Astro, puntando all'istanza Directus di produzione. Non va eseguito sul server né su cPanel.

  • Verifica che nel file .env locale siano già impostate le variabili Directus (passo 1.5) 
    DIRECTUS_URL=https://cms.tuodominio.it
DIRECTUS_TOKEN=token_generato_al_passo_1.4
  • Esegui lo script dalla root della repo 
    node --env-file=.env scripts/setup-collections.mjs
    Il flag --env-file carica il .env automaticamente — Node.js non lo fa di default. Disponibile da Node 20.6+.
  • Verifica nel pannello Directus (https://cms.tuodominio.it/admin) che le collezioni siano state create correttamente
Cosa crea: tutte le 17 collezioni e-commerce con campi e relazioni — pages, posts, categories, portfolio, faq, site_settings, products, product_categories, product_variants, shipping_zones, orders, order_items, customers, coupons, gift_cards, contact_submissions, stock_notifications. Lo script è idempotente: se una collezione esiste già, la salta.
Ripristino da backup: se stai migrando un progetto esistente con restore.mjs, non eseguire questo script — le collezioni vengono ricreate dal backup.

1.7 Configurare i permessi

  • Settings → Roles → Public: permesso read su pages, posts, categories, portfolio, faq, site_settings, products, product_categories
  • Crea ruolo Customer: read su orders (filtro: customer_email = $CURRENT_USER.email)
  • Il ruolo Admin ha accesso completo (non modificare)

1.8 Attivare l'integrazione AI (Claude Code + MCP)

Il file .mcp.json nella root della repo configura il server MCP ufficiale di Directus per Claude Code. Claude Code risolve ${DIRECTUS_URL} e ${DIRECTUS_TOKEN} dall'ambiente shell al momento del lancio — non legge il .env automaticamente.

  • Assicurati che il .env locale contenga DIRECTUS_URL e DIRECTUS_TOKEN corretti (step 1.4 completato)
  • Lancia Claude Code tramite lo script incluso — fa il source .env e poi avvia claude: 
    npm run claude         # oppure: bash scripts/claude.sh
    Mai usare il comando claude direttamente dalla shell: le variabili non sarebbero esportate e il server MCP non si connetterebbe a Directus.
  • Nella sessione Claude Code, verifica la connessione con /mcp — dovrebbe comparire directus con status connected
Alternativa rapida (sessione singola):
set -a && source .env && set +a && claude
Da usare se non vuoi aggiornare il progetto client con lo script.

2Stripe — Pagamenti e webhook

2.1 Creare account e ottenere le chiavi API

  • Crea account su dashboard.stripe.com (o accedi se già esistente)
  • Completa la verifica identità per attivare i pagamenti reali
  • Vai su Developers → API keys
  • Copia Publishable key (pk_live_...) → STRIPE_PUBLISHABLE_KEY
  • Clicca Reveal live key, copia Secret key (sk_live_...) → STRIPE_SECRET_KEYLa secret key è visibile una sola volta. Salvala subito in un password manager.
Differenza test/live: In sviluppo usa le chiavi pk_test_... / sk_test_.... Le carte di test sono disponibili su docs.stripe.com/testing. Carta di test universale: 4242 4242 4242 4242, qualsiasi scadenza futura, qualsiasi CVC.

2.2 Configurare il webhook

Il webhook notifica il backend quando un pagamento è completato.

  • Vai su Developers → Webhooks → Add endpoint
  • Endpoint URL: https://tuodominio.it/api/webhook/stripe
  • Events: seleziona checkout.session.completed
  • Clicca Add endpoint → vai su Signing secret → copia il valore whsec_... → STRIPE_WEBHOOK_SECRET
In sviluppo locale: usa Stripe CLI per forwardare gli eventi. Installa da stripe.com/docs/stripe-cli poi esegui:
stripe listen --forward-to localhost:4321/api/webhook/stripeIl CLI stampa un webhook secret temporaneo (whsec_...) da usare in .env durante lo sviluppo.

3Google reCAPTCHA v3
  • Vai su google.com/recaptcha/admin → accedi con account Google
  • Clicca + per registrare un nuovo sito
  • Label: nome del progetto. Tipo: Score based (v3)
  • Domains: inserisci tuodominio.it (senza https://). Aggiungi anche localhost per sviluppo
  • Copia Site Key → PUBLIC_RECAPTCHA_SITE_KEYQuesta chiave è pubblica e va nel bundle JS del frontend
  • Copia Secret Key → RECAPTCHA_SECRET_KEYQuesta chiave è privata, usata solo server-side per verificare il token
Score: reCAPTCHA v3 assegna uno score da 0.0 (bot) a 1.0 (umano). Il valore minimo accettato è configurabile con RECAPTCHA_MIN_SCORE (default: 0.5). Abbassa a 0.3 se ricevi falsi positivi da utenti legittimi.

4Frontend Deploy — VPS con Node.js + PM2 + Nginx

Il progetto usa @astrojs/node in standalone mode. Directus e frontend girano sullo stesso VPS (es. Hetzner), nessun servizio esterno necessario.

Progetto clonato da una versione precedente del template? Se il package.json contiene ancora @astrojs/netlify, sostituiscilo con Node.js: 
npm remove @astrojs/netlify
npm install @astrojs/node
Poi aggiungi in scripts del package.json: 
"claude": "bash scripts/claude.sh",
"deploy": "bash scripts/deploy.sh"
E copia i file scripts/claude.sh, scripts/deploy.sh, ecosystem.config.cjs dalla repo template.
ALLOWED_ORIGIN deve corrispondere esattamente all'URL del sito (senza slash finale): 
ALLOWED_ORIGIN=https://tuodominio.it   # NO slash finale
Non usare * in produzione: esporrebbe il checkout e le API a chiamate da qualsiasi origine.

4.6 Build e deploy sul server

  • Crea la cartella frontend sul server (solo al primo deploy) 
    ssh deploy@ip-server "mkdir -p /var/www/cliente/frontend"
  • Build in locale (con Node 22) 
    npm run build
  • Carica i file sul server con il comando di deploy automatico 
    npm run deploy
    Lo script fa build → rsync dist/ + package.json → npm install --production → pm2 startOrRestart sul server. Richiede DEPLOY_HOST, DEPLOY_USER, DEPLOY_PATH, DEPLOY_PM2_APP nel .env locale.
  • In alternativa al deploy automatico — carica manualmente e avvia 
    rsync -avz --delete dist/ deploy@ip-server:/var/www/cliente/frontend/dist/
rsync -avz ecosystem.config.cjs deploy@ip-server:/var/www/cliente/frontend/
rsync -avz .env.production deploy@ip-server:/var/www/cliente/frontend/.env
    In alternativa: git clone + npm run build direttamente sul server.
  • Sul server — installa le dipendenze e avvia con PM2 
    cd /var/www/cliente/frontend
nvm use 22
npm install --production
pm2 startOrRestart ecosystem.config.cjs --update-env
pm2 save
    Con @astrojs/node standalone mode il dist/ non include le dipendenze — è necessario npm install sul server. Porta sempre package.json e package-lock.json insieme al dist/.

4.7 Nginx vhost (frontend)

Il vhost per cms.tuodominio.it è già stato creato al passo 1.3 Opzione D. Qui si creano i vhost per staging e produzione (come root). Crea prima lo staging — è quello che userai per i test; il vhost di produzione puoi aggiungerlo subito o al momento del go-live (sezione 7).

VPS con più progetti: scegli una porta libera prima di configurare il vhost.
Ogni frontend Node.js deve girare su una porta diversa. Verifica quelle già in uso: 
pm2 list                             # mostra i processi attivi e i nomi
ss -tlnp | grep node               # mostra le porte occupate dai processi Node
Scegli una porta libera (es. 4321, 4322, 4323…) e impostala in due posti:
  1. Nel .env locale: DEPLOY_PORT=4322 e DEPLOY_PM2_APP=nomeprogetto
  2. Nel vhost Nginx: proxy_pass http://127.0.0.1:4322;
npm run deploy passa automaticamente DEPLOY_PORT a ecosystem.config.cjs via shell.
  • Crea il file vhost per lo staging 
    nano /etc/nginx/sites-available/staging.tuodominio.it
    Incolla il seguente contenuto: 
    server {
    server_name staging.tuodominio.it;

    location /.well-known/acme-challenge/ {
        root /var/www/html;
    }

    location / {
        proxy_pass http://127.0.0.1:DEPLOY_PORT;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }

    listen 80;
}
  • Crea il file vhost per il dominio di produzione (puoi farlo ora o al go-live) 
    nano /etc/nginx/sites-available/tuodominio.it
    Incolla il seguente contenuto: 
    server {
    server_name tuodominio.it www.tuodominio.it;

    location /.well-known/acme-challenge/ {
        root /var/www/html;
    }

    location / {
        proxy_pass http://127.0.0.1:DEPLOY_PORT;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }

    listen 80;
}
  • Abilita i siti, verifica la sintassi e ricarica Nginx 
    ln -s /etc/nginx/sites-available/staging.tuodominio.it /etc/nginx/sites-enabled/
ln -s /etc/nginx/sites-available/tuodominio.it /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx
    Se vuoi abilitare solo lo staging per ora, ometti il secondo ln e aggiungilo al momento del go-live.

4.8 DNS e SSL (frontend)

Ordine obbligatorio: i record DNS devono puntare all'IP del VPS prima di eseguire certbot. Il record cms è già stato configurato al passo 1.3 Opzione D.
  • Aggiungi i record DNS nel pannello del tuo provider (Hetzner DNS, cPanel Zone Editor, Cloudflare, ecc.)
    TipoNomeValoreTTLQuando
    AstagingIP VPS300ora
    A@IP VPS300al go-live
    AwwwIP VPS300al go-live
  • Verifica la propagazione DNS per lo staging 
    dig +short staging.tuodominio.it   # deve restituire l'IP del VPS
  • Rilascia il certificato SSL per lo staging 
    certbot --nginx -d staging.tuodominio.it
  • Rilascia il certificato SSL per il dominio di produzione (al go-live, dopo aver verificato il DNS) 
    dig +short tuodominio.it       # deve restituire l'IP del VPS
dig +short www.tuodominio.it   # idem
    certbot --nginx -d tuodominio.it -d www.tuodominio.it
    Certbot è già installato dal passo 1.3 Opzione D. Se stai facendo il deploy su un server diverso: apt install -y certbot python3-certbot-nginx.
  • Verifica il rinnovo automatico 
    certbot renew --dry-run
    I certificati Let's Encrypt scadono dopo 90 giorni. Certbot installa un timer systemd che rinnova automaticamente — --dry-run simula il rinnovo senza emettere un certificato reale.
Verifica finale: apri https://cms.tuodominio.it/admin e https://tuodominio.it nel browser — il lucchetto verde conferma che SSL è attivo su entrambi.

4.9 Backup cron

Il backup si configura come cron job di sistema sul VPS:

crontab -e
# Backup giornaliero alle 2:00
0 2 * * * cd /var/www/cliente/frontend && node scripts/backup.mjs >> /var/log/backup-cliente.log 2>&1
Vedi Fase 5 per la configurazione completa del backup (chiave admin, S3, ecc.).

5Backup automatico

5.1 Generare BACKUP_ADMIN_KEY

La chiave protegge l'endpoint /api/admin/backup da accessi non autorizzati. Deve essere una stringa casuale sicura:

# Genera una chiave sicura con Node.js
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

# Oppure con openssl
openssl rand -hex 32

Copia l'output → BACKUP_ADMIN_KEY nel file .env locale e sul server.

5.2 Schedule cron

Configura il cron job sul VPS (vedi 4.9). Esempi di schedule:

# Nel crontab del server (crontab -e)
0 2 * * *   # ogni giorno alle 02:00
0 2 * * 0   # ogni domenica alle 02:00
0 2 1 * *   # il primo del mese alle 02:00

5.3 Storage S3 (opzionale)

Per archiviare i backup su cloud (AWS S3, Backblaze B2, Cloudflare R2, MinIO):

  • Crea un bucket S3 dedicato al progetto
  • Crea un utente IAM con permesso s3:PutObject sul solo bucket
  • Genera Access Key + Secret Key per l'utente IAM
  • Imposta BACKUP_STORAGE=s3 e compila tutte le variabili BACKUP_S3_*

7Da staging a produzione — Spostare il frontend

Usa questa procedura quando il frontend è attivo su staging.tuodominio.it e vuoi spostarlo sul dominio definitivo tuodominio.it. Il CMS su cms.tuodominio.it rimane invariato.

7.1 Aggiorna le variabili d'ambiente

In locale, aggiorna il file .env:

PUBLIC_SITE_URL=https://tuodominio.it
ALLOWED_ORIGIN=https://tuodominio.it
Rebuild obbligatorio: PUBLIC_SITE_URL viene embedded nel bundle SSG durante la build (sitemap, canonical, OG tags). Senza rebuild il sito continuerà a indicare il vecchio dominio nei metadati.

7.2 Build e deploy sul nuovo dominio

Fai il deploy prima di cambiare il DNS — il server viene aggiornato mentre il vecchio dominio è ancora attivo:

npm run deploy
Lo script rebuilda con i nuovi env vars, sincronizza il dist/ sul server e riavvia PM2.

7.3 Crea il vhost Nginx per il dominio definitivo

Sul server come root, crea un nuovo vhost senza rimuovere quello di staging:

nano /etc/nginx/sites-available/tuodominio.it
server {
    server_name tuodominio.it www.tuodominio.it;

    location /.well-known/acme-challenge/ {
        root /var/www/html;
    }

    location / {
        proxy_pass http://127.0.0.1:DEPLOY_PORT;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }

    listen 80;
}
ln -s /etc/nginx/sites-available/tuodominio.it /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx

7.4 DNS — aggiungi i record per il dominio definitivo

  • Aggiungi i record A nel pannello del tuo provider
    TipoNomeValoreTTL
    A@IP VPS300
    AwwwIP VPS300
  • Verifica propagazione prima di procedere con certbot 
    dig +short tuodominio.it       # deve restituire l'IP del VPS
dig +short www.tuodominio.it   # idem
  • Ottieni il certificato SSL per il dominio definitivo 
    certbot --nginx -d tuodominio.it -d www.tuodominio.it

7.5 Aggiorna i servizi esterni

  • Stripe webhook — Developers → Webhooks → aggiorna URL endpoint da staging.tuodominio.it/api/webhook/stripe a tuodominio.it/api/webhook/stripeIl STRIPE_WEBHOOK_SECRET cambia — aggiorna il .env locale e rideploya (npm run deploy).
  • reCAPTCHA — google.com/recaptcha/admin → aggiungi tuodominio.it ai domini autorizzati (puoi lasciare anche staging.tuodominio.it)
  • Directus CORS — se hai configurato CORS_ORIGIN nel .env di Directus, aggiorna il valore con il nuovo dominio

7.6 Rimozione staging (opzionale)

Una volta verificato il funzionamento su tuodominio.it, puoi dismettere il dominio di staging:

  • Rimuovi il vhost staging da Nginx 
    rm /etc/nginx/sites-enabled/staging.tuodominio.it
nginx -t && systemctl reload nginx
  • Revoca o lascia scadere il certificato staging (opzionale — non causa problemi se rimane)
  • Rimuovi il record DNS staging dal pannello del provider
Verifica finale: apri https://tuodominio.it, effettua un ordine di test con la carta Stripe 4242 4242 4242 4242 e verifica che il webhook sia recapitato correttamente.
